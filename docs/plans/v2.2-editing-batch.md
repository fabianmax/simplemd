# v2.2 — editing batch: table cells, ⌘-click links, Tab

Three asks from the roadmap (#13, #14, #15). Two are small and one of them
quietly asks whether this editor is still the thing CLAUDE.md says it is, so it
goes first.

## #13 — editing a table cell without dropping to raw source

Today a click in a rendered table lands the cursor in the right cell (#2) and
the whole table flips to pipe syntax. For a four-column table that is unreadable
— which is the exact reason the widget exists. The ask: keep the table rendered
and edit the one cell.

**The constraint this runs into.** The core invariant: *the buffer is the source
text, rendering is view-only decoration, nothing ever re-serializes the
document.* Making the rendered HTML editable and converting it back to markdown
would break that — a cell holding `**bold**` would come back as whatever our
serializer felt like that day, and every subsequent agent diff would be noise.

**The way through: per-cell source reveal.** The per-line reveal rule that the
whole live preview is built on, applied one level down:

- Click a cell → *that cell* shows its raw source (`**bold**`, not **bold**) and
  becomes an editable island. The table keeps its layout; every other cell stays
  rendered.
- Every keystroke writes back into exactly that cell's range in the buffer. A
  targeted replacement, the same shape as any other command in `format.ts`.
- Blur → the cell renders again.

So the reader edits markdown, sees a table, and the invariant never bends. The
cell boundaries already exist: `live-preview/table.ts` (`splitRow`, `cellPos`)
was written for #2 and gives the source range of any (row, col).

**Why an editable island inside a widget is safe.** CM's DOM observer drops
mutations inside widgets — `readMutation` returns `null` when the nearest tile
`isWidget()`. Nothing the browser does inside the cell reaches the document
model; every change is one we dispatch ourselves. The wrapper stays
`contenteditable="false"` and only the focused cell is `true`, so the cell is
its own editing host.

**The hazard is the rebuild, not the typing.** Our own write changes the doc →
the decoration field rebuilds → a new `TableWidget` → CM would replace the DOM
and the caret with it. Two defences:

- `eq()` keeps comparing source, but `updateDOM()` is implemented: when the DOM
  it is handed contains the focused cell, it leaves the DOM alone and returns
  true. Typing therefore never re-renders the table under the caret.
- The CM selection is *not* moved into the table on a cell click (the checkbox
  widget already sets this precedent). If it were, the reveal predicate would
  turn the whole table to source — the thing we are removing.

**Keys inside a cell:** `Tab`/`⇧Tab` commit and move to the next/previous cell,
`Escape` hands focus back to the editor, `Enter` is swallowed (a newline cannot
live in a GFM cell). A typed `|` is escaped to `\|` on the way in, or it would
split the row.

**What is deliberately not in scope:** adding or removing rows and columns,
alignment, column drag. That is a table editor, and this is a review surface.
⌘E still shows the whole file as source, which is where structural table edits
belong.

## #14 — ⌘-click opens links, plain click puts the cursor

A plain click currently always follows the link, which makes the most ordinary
gesture in a rendered document ambiguous: click beside a link and you are
editing, click on it and you are in a browser.

- Plain click: cursor, like any other text. The line reveals its source, which
  is how the link gets edited.
- ⌘-click: opens. Same inside a rendered table cell.
- Affordance: while ⌘ is held, links take the pointer cursor and an underline;
  the link decoration carries a `title` so a hover says it in words.

This deletes the drag-threshold special case in `app.ts`, which only ever
existed because a plain click had two meanings.

## #15 — Tab

Tab does nothing today.

**What it inserts: two spaces.** Not a tab character — CommonMark advances a
hard tab to the next four-column stop and renderers disagree about the rest,
while spaces mean what they look like. Not four either: two is CodeMirror's
default indent unit and exactly the width of `- `, so an indented bullet lines
up under its parent's text.

**On a list line Tab is a level change, not a blind indent.** The line is
re-indented to the *content offset of the nearest item above it at the same
level* — 2 for `- parent`, 3 for `1. parent` — which is what CommonMark requires
for the item to nest instead of starting a new list. `⇧Tab` drops it to the
enclosing item's indent. Numbers are never rewritten: a nested ordered list
starting at `2.` is valid markdown and renumbering it would be a
re-serialization.

**Everywhere else** Tab inserts the indent unit at the cursor, and with a
multi-line selection Tab/⇧Tab indent and outdent every selected line.

All of it is pure `EditorState → TransactionSpec`, so it lands in `format.ts`
next to the other commands and is tested headless.

**Accessibility note, stated rather than solved:** binding Tab takes it from
focus navigation, which is why CM6 leaves it unbound by default. Every other
surface in this window is reachable by a ⌘ shortcut, so the trap is shallow.

## Order and verification

1. #15 (pure, no DOM) — the shortest path to something runnable.
2. #14 (one handler, one decoration, CSS).
3. #13 last, because it is the one that can fight WKWebView.

Headless covers the cell mapping, the write-back specs and the indent commands.
The editable island has to be tried in the real app: jsdom will happily focus a
`contenteditable` and fire `input`, and prove nothing about whether WKWebView
keeps the caret when a widget's DOM is left alone. If it does fight us, the
fallback is a positioned overlay input rather than an island — same write-back,
different carrier.
